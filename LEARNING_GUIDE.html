Part A — The mental model

What "the engine" is

The engine is a Python module collection that turns one messy cap-table .xlsx into a Big 4 portable bundle.zip with every analyst decision recorded in an append-only hash chain. The user-facing surface is a Flask app serving both an HTMX-driven browser UI and a JSON REST API from the same endpoints.

The two-layer split

Every piece of work in this codebase sits on one of two sides of a hard line:

Pure compute layerPersisted engagement layer
Takes a CapTable and returns a result. No I/O, no DB, no Flask. Deterministic: same input always produces identical output (modulo timestamp carve-outs). Takes user actions, validates them against role + concurrency + business rules, and writes immutable records. Stateful: every mutation appends to the hash chain.
Examples: waterfall.py, checklist.py, diff.py, snapshot_timeline.py, opm/backsolve.py, diff_workpaper.py. Examples: engagement.py (the EngagementStore), engagement_routes.py, engagement_bundle.py, token_deny.py.

The split matters because pure-compute code can be tested without a Flask app, an SQLite DB, or a Pydantic model boundary. Persisted-layer code has to be tested against a real store with real concurrency semantics. Keeping them separate is what made it possible to ship 842 regression tests at ~60 seconds runtime.

The audit loop as a build discipline

Every wave follows the same six-step ritual:

  1. Build the planned items (5 to 13 per wave).
  2. Test with per-item regression coverage.
  3. Dispatch an independent auditor against ONLY the wave's deltas.
  4. Triage findings into fix-now vs defer with rationale.
  5. Fix with one regression test per audit finding ID.
  6. Document in BUILD_WAVE_N.md + SYSTEM_AUDIT_WAVE_N.md.

Why this matters: the audit is a forcing function. The builder is blind to their own assumptions. The auditor reads the code with no context and asks "why?" at every seam. Every finding gets a stable ID (B-W7-1, W9-M3, etc.) and that ID becomes the regression test name. When a future change re-introduces the bug, the test fails with the finding code in its name, and the audit doc explains the original context. You can't lose the lesson.

Part B — How the engine works (request lifecycle)

Walk one request end-to-end. The analyst clicks "Upload" on the engagement detail page. Their browser sends: 

POST /engagement/abc-123/upload?html=1 HTTP/1.1
Cookie: qapita_session=<hmac-signed>; qapita_csrf=<random>
Content-Type: multipart/form-data; boundary=...

[file bytes]
csrf_token: <matches the cookie>
expected_version: 2
change_note: Series C closing 2026-03-15

Stage 1 — Flask routing

Flask matches the path against the engagement blueprint (url_prefix="/engagement"). The matched view is engagement_routes.upload(eng_id="abc-123").

Stage 2 — Phase-0 demo gate

An app-level before_request hook checks whether the path matches any phase-0 demo route (/upload, /whatif/, etc.) and refuses with 404 phase-0-demo-disabled unless ALLOW_PHASE_0_DEMO=1 is set. This request goes to /engagement/... so the gate doesn't fire.

Stage 3 — Auth resolution (engagement blueprint before_request)

_require_user() runs. It looks up credentials in this order:

  1. Bearer token from Authorization: Bearer <tok> header. Explicit beats ambient.
  2. If no Bearer, session cookie via resolve_session_cookie().
  3. Otherwise: 401 with WWW-Authenticate: Bearer for API clients, or 302 to /login for browsers.

Before authenticating, the Bearer is checked against the deny list (token_deny.is_revoked). A revoked Bearer authenticates as nobody and falls through to the cookie path or 401. The resolved user is stashed on g.current_user; the credential type is stashed on g.auth_source = "bearer" | "cookie".

Stage 4 — CSRF check (cookie path only)

If g.auth_source == "cookie", verify_csrf() runs. It reads the qapita_csrf cookie value and compares it (constant-time via hmac.compare_digest) against the X-CSRF-Token header OR the csrf_token form field. Mismatch returns 403 csrf-mismatch; missing cookie returns 403 csrf-missing-cookie. Bearer requests skip this entirely (the Bearer IS the credential, not ambient session).

Stage 5 — Route handler

The upload view runs. It checks engagement.upload_cap_table permission against g.current_user.role. Validates the file extension. Rejects control chars in change_note. Calls parse_excel to turn the bytes into a CapTable model. Wraps in try/finally so the workbook handle closes on any exception path.

Stage 6 — Store mutation under lock

store.add_snapshot(actor, engagement_id, expected_version, cap_table, ...) acquires a process-local RLock, re-reads the engagement, verifies eng.version == expected_version (raises EngagementVersionConflict if not), then runs an atomic conditional UPDATE: 

UPDATE engagement
   SET head_snapshot_id = ?, version = version + 1
 WHERE id = ? AND version = ?

If cur.rowcount != 1, raises EngagementVersionConflict (defense in depth — the lock prevents this in single-process, but the rowcount check would catch multi-process races too). Then INSERTs the snapshot row.

Stage 7 — Audit event append

_append_audit_event computes: 

prev = engagement.audit_head_hash  # "00" * 32 at genesis
canonical = f"{event_type}|{actor}|{ts_iso}|{payload_json}"
row_hash = sha256(prev.encode() + b"\x00" + canonical.encode()).hexdigest()

Inserts the audit_event row, then UPDATEs engagement.audit_head_hash = row_hash. All inside the same _write_lock so the chain stays monotonic.

Stage 8 — Response shape (content negotiation)

_wants_html() checks ?html=1 first, then parses the Accept header with q-value support (text/html;q=0.9, application/json;q=0.5). Returns True if the highest-q match is HTML.

  • If HTML: 302 redirect to /engagement/abc-123?html=1.
  • If JSON: 201 Created with {snapshot_id, engagement_version, warnings}.

Stage 9 — after_request CSRF management

_heal_csrf_cookie attaches a new CSRF cookie if _inject_csrf decided to mint one (auto-heal for missing cookies or rotation for stale ones). Decision lives in _inject_csrf so the template's hidden input and the response cookie always agree on the same token value (the wave-9 B-W9-B1 fix).

Stage 10 — Browser follows redirect

Browser GETs /engagement/abc-123?html=1. Same auth stages run. View renders detail.html with the new head snapshot, the 60-rule findings list, and the resolve-form per finding.

Part C — Concepts that built this, explained from first principles

Each concept follows the same template: what it is, why we need it, how it works mechanically, what alternatives we rejected, where it lives in the code.

1. Pydantic v2 schema-first models

What A Python library that turns class definitions into runtime-validated, JSON-serialisable schemas.
Where src/models.py, src/engagement.py (Snapshot, Resolution, Engagement, AuditEvent).

Why we need it. The Excel parser produces a dict-shaped blob with mixed types, missing fields, and ad-hoc shapes. Without a validated schema, downstream code has to defensively check every attribute access. With Pydantic, validation happens once at the boundary; everything downstream gets a typed object it can rely on.

How it works. You declare a model with type annotations: 

class ShareClass(BaseModel):
    model_config = ConfigDict(extra="forbid")  # reject unknown fields
    name: str
    type: ShareClassType
    shares_outstanding: int = Field(..., ge=0)
    issue_price: Optional[float] = None
    liquidation_preference: Optional[LiquidationPreference] = None

Pydantic generates a validator at class-creation time. Calling ShareClass(**raw_dict) coerces types, runs field validators, and raises ValidationError if anything is off. model_dump_json(indent=2) serialises deterministically with sorted keys.

What we rejected. Hand-rolled dataclasses with manual validation (verbose), or untyped dicts everywhere (a graveyard of KeyError bugs). Pydantic v2 is rewritten in Rust under the hood; the validation overhead is negligible.

The trap to know. extra="forbid" on every model. Without it, a typo in the parser silently passes through as an extra field nobody reads.

2. Hash-chained audit log

What A sequence of records where each row's SHA-256 hash includes the previous row's hash, making any tampering detectable offline.
Where src/engagement.py — _append_audit_event, verify_audit_log, _compute_row_hash.

Why we need it. Big 4 auditors will pull the bundle six months after engagement close and need to prove every analyst decision happened in the order recorded, without trusting the running system. A linear log with timestamps proves nothing — a malicious admin can edit any row. A hash chain proves that any edit to row N invalidates the hashes of rows N+1, N+2, ..., HEAD.

How it works. Genesis hash is 64 zero hex chars. Each row computes: 

canonical_payload = f"{event_type}|{actor}|{ts_iso}|{payload_json}"
# payload_json is canonical: sort_keys=True, separators=(",", ":")
row_hash = SHA256(prev_row_hash.encode() + b"\x00" + canonical_payload.encode()).hexdigest()

The engagement table stores the current HEAD hash. Each new event reads HEAD, computes the new row's hash, INSERTs the row, and UPDATEs HEAD. Inside a single _write_lock so the chain stays monotonic.

Offline verification recipe. Auditor reads audit_log.jsonl line by line. Starts prev = "00" * 32. For each event, recomputes the SHA-256 from prev + the stored canonical payload. If it matches the stored row_hash, the row is intact. Sets prev = row_hash. Continues. The final row's hash MUST match manifest.audit_head_hash.

What we rejected. Signing each row with a private key (overkill — we only need tamper-evidence, not non-repudiation). Merkle trees (Bitcoin-style — overkill for a linear log).

3. Optimistic concurrency via atomic conditional UPDATE

What A pattern that lets two clients write to the same row safely without locking, by attaching a version number to every mutation.
Where src/engagement.py — every mutating method.

Why we need it. Two analysts open the same engagement page at version 5. Both click "Move to review" simultaneously. Without guarding, one overwrites the other and the audit log loses a state transition.

How it works. Every mutating route requires the caller to send expected_version matching what they last read. The store does: 

cur = conn.execute(
    "UPDATE engagement SET status = ?, version = version + 1 "
    "WHERE id = ? AND version = ?",
    (new_status.value, engagement_id, expected_version),
)
if cur.rowcount != 1:
    raise EngagementVersionConflict(engagement_id, expected_version, current)

The WHERE id = ? AND version = ? clause is the magic. If the version no longer matches what the client saw, the UPDATE affects zero rows. cur.rowcount == 0 tells us unambiguously that someone else won the race. We raise a 409 engagement-version-conflict and the client retries after re-reading.

The defense-in-depth twist. We also hold a process-local RLock across the read-then-write. In single-process Flask, the lock alone is sufficient. The rowcount check is what makes the contract survive a multi-process deploy (gunicorn workers, k8s pods).

What we rejected. Pessimistic locking (SELECT FOR UPDATE) — works on Postgres but doesn't have meaningful semantics in SQLite's serialized journal mode. Last-write-wins (no version check) — silently loses concurrent edits, the exact bug we wanted to prevent.

4. HMAC-signed session cookies

What An opaque cookie value containing user identity + expiry, signed with a server-side secret so the browser can't tamper with it.
Where src/cookie_auth.py — issue_session_cookie, verify_session_cookie.

Why we need it. Browsers can't attach Authorization: Bearer headers to plain <a href=...> links, so the wave-4 HTMX UI was dev-only until we added cookie auth. The cookie carries enough info for the server to identify the user on subsequent requests, without a database session table.

How it works. Cookie format: 

payload = f"{user_id}|{expiry_iso}".encode("utf-8")
sig = hmac.new(secret_key, payload, hashlib.sha256).digest()
cookie_value = b64url(payload) + "." + b64url(sig)

The server reads the cookie, splits on ., recomputes the HMAC from its own copy of secret_key, and compares with hmac.compare_digest (constant-time, defeats timing attacks). If the comparison passes and the expiry is in the future, the cookie is valid.

Cookie attributes.

  • httponly=True: JS can't read the cookie. Defeats one class of XSS exfiltration.
  • samesite="Strict": Browser refuses to send the cookie on cross-site requests. Defeats most CSRF in modern browsers.
  • secure=True (non-TESTING): Browser refuses to send over plain HTTP. Defeats network MITM.

What we rejected. Flask's built-in flask.session uses itsdangerous which is similar but serializes the whole dict. We wanted a tiny, audited surface. JWT — overkill for a single-server app; we don't need claims, just identity.

5. CSRF double-submit cookie pattern

What A defense against cross-site request forgery that requires the form to echo a value from a cookie. An attacker site can submit forms but can't read the cookie, so they can't forge the matching field.
Where src/cookie_auth.py — issue_csrf_token, verify_csrf; src/engagement_routes.py — _inject_csrf + _heal_csrf_cookie.

Why we need it. An attacker hosts a page that POSTs to your /engagement/<id>/transition route. If the victim is logged in (session cookie in their browser), the browser sends the cookie with the cross-site POST. Without CSRF protection, the attacker just changed the engagement state. SameSite=Strict defeats most of this in modern browsers but not all paths.

How it works. Server issues two cookies at login: qapita_session (HttpOnly) and qapita_csrf (NOT HttpOnly, so JS can read it). Forms include <input type="hidden" name="csrf_token" value="..."> with the value JS read from the cookie. Server verifies the form field equals the cookie via hmac.compare_digest.

The attacker site can't read the cookie (same-origin policy), so it can't forge the matching form field. The protection holds even without HMAC signing the token — the secret is the cookie value the attacker can't see.

The Bearer carve-out. CSRF check only fires when g.auth_source == "cookie". Bearer-authenticated requests are exempt because the Bearer IS the explicit credential, not an ambient session a cross-site attacker can ride on.

Token rotation (W9.5). CSRF tokens encode <unix_seconds>.<random>. The engagement blueprint's after_request rotates the cookie when its age > 1 hour. A leaked token's blast radius drops from 7 days to 1 hour. The decision lives in _inject_csrf so the template's hidden input and the response cookie always agree on the same value (the original W9.5 placed rotation in after_request and broke this — wave-9 audit B-1).

What we rejected. Flask-WTF (extra dependency we didn't need; CSRF as a single decorator was sufficient). Synchronizer token pattern (requires server-side storage of all valid tokens).

6. Bearer token revocation deny list

What A small server-side table of revoked Bearer tokens. Logging out adds the token's hash. The auth guard checks the list before identity resolution.
Where src/token_deny.py — TokenDenyList.

Why we need it. Cookie logout is easy (clear the cookie). Bearer logout is harder because the token lives on the client. Without revocation, "log me out" only ends the browser session; an API client holding the Bearer can keep making requests until the SSO provider expires the token.

How it works. SQLite table: 

CREATE TABLE token_deny (
    token_hash TEXT PRIMARY KEY,
    revoked_at REAL NOT NULL,
    expires_at REAL NOT NULL DEFAULT 0
);

POST /logout with Authorization: Bearer <tok> computes SHA-256(tok) and INSERTs the hash with expires_at = now + 30 days. The auth guard does a SELECT 1 FROM token_deny WHERE token_hash = ? before calling provider.authenticate(token). Denied tokens resolve to nobody.

Why hash, not raw. A database compromise would leak live credentials if we stored raw tokens. SHA-256 is one-way; the attacker gets the deny list but not the working tokens.

Why TTL. Without expiry, the table grows monotonically forever. Lookup latency walks up. With TTL matching the SSO provider's max token lifetime, prune jobs can drop entries that would have expired upstream anyway. flask --app app prune-deny-list runs the cleanup.

What we rejected. Calling the SSO provider's revocation endpoint on every request (latency + reliability cost). No revocation at all (the wave-6 audit blocker — "Bearer not revoked by /logout" — is exactly this).

7. SQLite WAL mode + per-process cached connections

What Two performance hardenings on the deny list (and any other hot-path SQLite store).
Where src/token_deny.py __init__.

Why we need it. The original wave-6 deny list opened and closed a fresh SQLite connection per is_revoked() call. On the engagement blueprint's hot path (every authenticated request), this is one fopen + fclose + fsync per HTTP call. The wave-6 audit M-W7-2 flagged it as an operational footgun.

WAL mode (Write-Ahead Logging). Default SQLite uses the rollback journal: writers block readers. WAL flips this: writes go to a separate log file, readers read from the main DB at their snapshot, writes commit by atomically moving the log into the main DB. Readers don't block writers and vice versa. Set with PRAGMA journal_mode=WAL.

synchronous=NORMAL. WAL's default sync mode is FULL, which fsyncs on every commit. NORMAL skips some fsyncs and is durable enough for our use (a power loss might lose the last millisecond of writes; SQLite's authors document this as the recommended setting for WAL).

Cached connection. Single sqlite3.Connection(check_same_thread=False, isolation_level=None) per process. Threaded under a RLock so concurrent calls serialise correctly. Eliminates the fopen + fclose + fsync per call.

What we rejected. Connection pool (overkill for a single-file SQLite store). In-memory SQLite (would lose state on restart).

8. Byte-stable xlsx output

What Two consecutive builds of the same xlsx workbook produce identical SHA-256.
Where src/xlsx_stability.py — pin_workbook_properties + stabilise_xlsx_bytes.

Why we need it. The bundle ships a SHA-256 manifest; the auditor recomputes hashes offline to verify nothing was modified after generation. If the xlsx producer leaks wall-clock timestamps into the output, every regeneration produces different bytes and the manifest's claim "bit-for-bit reproducible" is false.

What openpyxl does wrong by default. Three sources of non-determinism:

  1. docProps/core.xml writes dcterms:created + dcterms:modified with wall-clock timestamps.
  2. Even if you pin wb.properties.created, openpyxl OVERRIDES dcterms:modified at save() with wall-clock.
  3. Each zip entry's date_time field is wall-clock by default.

The fix. Two-stage:

  1. Before save(), pin wb.properties.{created, modified, creator, lastModifiedBy} via pin_workbook_properties(wb, anchor). Anchor is typically engagement.created_at — a stored timestamp the analyst can re-derive.
  2. After save(), run stabilise_xlsx_bytes(blob). This reads the zip, rewrites every entry with ZipInfo(date_time=(1980,1,1,0,0,0)) (DOS epoch), AND scrubs dcterms:modified in docProps/core.xml to match the pinned dcterms:created.

Result: build_diff_workpaper_xlsx(diff) called twice 1.1s apart returns identical bytes.

What we rejected. Monkey-patching openpyxl internals (fragile across upstream releases). Writing the xlsx zip from scratch (would lose openpyxl's correct formula + styling serialisation).

9. Content negotiation (HTML vs JSON from one route)

What One Flask route serves both an HTMX-rendered HTML page and a JSON API response depending on the client's preference.
Where src/engagement_routes.py — _wants_html() + _engagement_errors decorator.

Why we need it. Wave 4 added a browser UI on top of the existing JSON API. We didn't want to fork every route into /engagement/x + /ui/engagement/x — that's twice the test surface and twice the chance of drift.

How it works. 

def _wants_html() -> bool:
    if request.args.get("html") == "1": return True
    accept = request.headers.get("Accept", "").lower()
    if not accept: return False
    # Parse "text/html;q=0.9, application/json;q=0.5"
    types = []
    for chunk in accept.split(","):
        parts = [p.strip() for p in chunk.strip().split(";")]
        media = parts[0]; q = 1.0
        for p in parts[1:]:
            if p.startswith("q="): q = float(p[2:])
        types.append((media, q))
    types.sort(key=lambda t: t[1], reverse=True)
    for media, _q in types:
        if media in ("text/html", "application/xhtml+xml"): return True
        if media == "application/json": return False
    return False  # curl's */* defaults to JSON

Each route ends with: 

if _wants_html():
    return render_template("engagement/detail.html", engagement=eng, ...)
return jsonify(eng.model_dump(mode="json"))

Error responses too. The _engagement_errors decorator catches typed exceptions (EngagementError subclasses) and branches on _wants_html() — returns the styled error page for browsers, structured JSON for API clients. Same HTTP status code either way.

Why the explicit ?html=1. Some HTMX form posts arrive with Accept: */*. The explicit query flag is the reliable signal.

10. Role-based access control matrix

What A flat dict mapping roles to permission strings. Every mutating call checks the user's role against the action being requested.
Where src/identity.py — _PERMISSIONS + can(user, action).

Why we need it. Four roles in the system: analyst, reviewer, partner, read-only auditor. Each has a different scope. Spec §3.2 codifies the matrix. Without enforcement, the spec is just a wish.

How it works. One flat dict literal: 

_PERMISSIONS: dict[Role, frozenset[str]] = {
    Role.analyst: frozenset({
        "engagement.create", "engagement.read",
        "engagement.upload_cap_table", "engagement.add_snapshot",
        "engagement.resolve_finding",
        "engagement.transition_open_to_review",
        "export.json", "export.xlsx", "export.memo_pdf",
    }),
    Role.partner: frozenset({
        "engagement.read", "engagement.add_snapshot",
        "engagement.resolve_finding", "engagement.add_reviewer_note",
        "engagement.transition_review_to_signed",
        "engagement.transition_signed_to_review",  # GAP-29 reopen
        "engagement.transition_review_to_open",
        "engagement.transition_to_archived",
        "engagement.restore_archived",  # W8.10 90-day window
        "engagement.pii_redact",  # GAP-03
        "export.json", "export.xlsx", "export.memo_pdf",
    }),
    # ... reviewer, read_only_auditor
}

def can(user: User, action: str) -> bool:
    return action in _PERMISSIONS.get(user.role, frozenset())

Every route does if not can(user, "engagement.X"): return 403. Transitions also map (from_status, to_status) to an action so the permission can be granular per state pair.

The dead-grant trap. Wave-5 audit M-3 caught a transition listed in _ALLOWED_TRANSITIONS with no role holding the matching permission — partners could see "review → open" in the spec but no role could trigger it. The fix was a one-line addition. The trap: keeping the transitions dict and the permissions dict in sync requires discipline.

11. Calendar-hour rate limiting buckets

What A per-user counter that increments on each request and resets at the top of every hour. Soft limit returns 429; hard limit writes an audit event.
Where src/rate_limit.py — ExportRateLimiter.

Why we need it. Bundle generation is expensive (rule pack re-run + xlsx + PDF + zip post-process). Without a rate limit, a misbehaving client can knock the engine over with a loop.

How it works. One SQLite row per (user_id, hour_bucket) where hour_bucket = floor(unix_seconds / 3600). consume(user_id): 

INSERT INTO export_counter (user_id, hour_bucket, count)
VALUES (?, ?, 1)
ON CONFLICT(user_id, hour_bucket) DO UPDATE SET count = count + 1

SELECT COALESCE(SUM(count), 0) AS n
  FROM export_counter
 WHERE user_id = ? AND hour_bucket = ?

Result: current_count. Compare to soft_limit (e.g. 30) and hard_limit (e.g. 100). Return 429 with Retry-After seconds until the bucket rolls over. At current == hard_limit, write a bulk_export_alert audit event (edge-triggered: fires exactly once at the boundary, not on every subsequent call).

The 2-bucket sum trap. Wave-5 audit M-8 caught the original implementation summing the current AND the previous bucket — which gave an effective window between 1h and 2h depending on position. Switched to single-bucket calendar-hour (the simpler contract spec §8.17 actually documents).

Why separate compute + export budgets. /whatif and /diff burn CPU but don't produce export artifacts. Sharing a budget with the memo path would mean a scenario-spamming analyst couldn't generate a memo. Two independent buckets (EXPORT_LIMITER at 30/hr, COMPUTE_LIMITER at 300/hr) decouple the contention.

12. Idempotent schema migrations

What Schema changes you can run safely on a fresh DB OR an already-migrated DB. No migration framework, no version table.
Where src/engagement.py EngagementStore.__post_init__; src/token_deny.py.

Why we need it. Multiple processes can boot simultaneously. The first one to run the migration wins; the others must tolerate "already migrated." Without a migration framework (Alembic etc.), every schema change has to be idempotent by construction.

How it works. The classic pattern: 

cols = {row["name"] for row in conn.execute("PRAGMA table_info(engagement)")}
if "bound_pack_json" not in cols:
    try:
        conn.execute("ALTER TABLE engagement ADD COLUMN bound_pack_json TEXT")
    except sqlite3.OperationalError as e:
        if "duplicate column name" not in str(e).lower():
            raise

PRAGMA table_info tells us what columns exist. ALTER TABLE ADD COLUMN with the try/except handles the race where two processes both pass the check before either commits. "duplicate column name" is the only acceptable failure mode here; everything else re-raises.

The legacy-row backfill (W8-m6). Adding a NOT NULL column to an existing table doesn't help legacy rows that already have a NULL there. The W8.10 archival migration ALSO backfills: 

rows = conn.execute(
    "SELECT id, created_at FROM engagement "
    "WHERE status = 'archived' AND archived_at IS NULL"
).fetchall()
for row in rows:
    base = datetime.fromisoformat(row["created_at"])
    restore_until = base + timedelta(days=ARCHIVAL_RESTORE_DAYS)
    conn.execute("UPDATE engagement SET archived_at = ?, "
                 "restore_eligibility_until = ? WHERE id = ?",
                 (base.isoformat(), restore_until.isoformat(), row["id"]))

Idempotent because subsequent runs find no rows to update (the columns are now populated).

13. Black-Scholes-Merton + brentq for OPM Backsolve

What The mathematical core of the OPM (Option Pricing Method) — model each waterfall tranche as a European call option and use a root-finder to back into the total equity value that matches the latest priced round's per-share price.
Where src/opm/backsolve.py — backsolve, _tranche_value; src/opm/bsm.py — the call pricing formula.

Why we need it. "OPM Backsolve" is the workhorse technique for 409A valuations. It says: if I know what the Series C investors just paid per share, what total equity value S would the model say is consistent with that price? Solve for S, then apply S to every other tranche to get per-class fair values.

How Black-Scholes fits in. Each waterfall breakpoint defines a tranche: between $X and $Y of exit value, this tranche pays out. Model each tranche as the difference of two European call options on S with strikes at X and Y. The call price formula: 

C(S, K, T, r, sigma) = S * N(d1) - K * exp(-r * T) * N(d2)
where d1 = (ln(S/K) + (r + sigma^2/2) * T) / (sigma * sqrt(T))
      d2 = d1 - sigma * sqrt(T)
      N = standard normal CDF

Subtracting C(K_upper) - C(K_lower) gives the value of that tranche. Sum across tranches that pay a given class and you get the class's total expected payout at total equity value S.

The root-find. We have a target: anchor class's per-share price = analyst-supplied value. We have a function: per_share(S) = total_payout_to_anchor(S) / anchor_shares. Define residual(S) = per_share(S) - target. The S we want is the root of residual. 

from scipy.optimize import brentq
S_star = brentq(residual, _S_LOWER, _S_UPPER, xtol=1e-3, rtol=1e-9)

brentq is Brent's method: a robust, bracketed root-finder that converges quadratically near the root and falls back to bisection if the quadratic step misbehaves. Needs the root bracketed (a sign change between _S_LOWER and _S_UPPER); raises if it can't.

What the tool DOES NOT do. Pick volatility. Pick time-to-liquidity. Pick risk-free rate. Pick DLOM. Those are the analyst's defended numbers. MarketInputs.__post_init__ (wave-9 audit M-2) rejects negative σ, NaN, Inf, out-of-range values so a sign typo doesn't silently produce "defendable" output (Black-Scholes squares σ; a negative σ is mathematically valid but semantically nonsense).

14. Jinja2 autoescape and the |safe trap

What Jinja2 auto-escapes HTML special chars in {{ var }} output. The |safe filter disables this. Misusing |safe is how XSS ships.
Where The wave-5 stitched audit's B-3 blocker; closed by switching to {{ chart | tojson }}.

Why it matters. Class names flow from the user-uploaded .xlsx straight through to JSON payloads rendered inside <script> tags for the waterfall chart. If we dump the JSON via {{ chart_json | safe }}, a class name containing </script><script>alert(1)</script> breaks out of the script tag and executes JS in the analyst's browser. Stored XSS, full session compromise.

The fix. Replace |safe with |tojson. Flask's tojson filter escapes <, >, &, ', U+2028, U+2029 — exactly the characters that would break out of <script> context. The literal </script> in input becomes in output, which JS happily parses as a normal string.

Defensive test. The regression test asserts "chart_json|safe" not in template_source so a future refactor can't quietly re-introduce the bug.

What we rejected. Manually escaping in Python before rendering (fragile, easy to miss a case). Embedding via <script type="application/json">...</script> + JSON.parse(document.getElementById('chart').textContent) (works but requires JS refactor; |tojson was cheaper).

15. PDPA redaction with audit-log preservation

What Right-to-erasure: PII in the cap-table can be zeroed without breaking the audit chain that proves it once existed.
Where src/engagement.py — redact_snapshot_pii; Snapshot.safe_change_note() + safe_source_filename() + safe_created_by().

Why we need it. PDPA (Singapore) and GDPR (EU) both grant data subjects a right to erasure. The cap table contains holder names that map to natural persons. We have to be able to scrub them without invalidating the integrity proofs.

How it works. Two complementary tactics:

  1. Sentinel-replace the PII column. redact_snapshot_pii UPDATEs the snapshot row: cap_table_json = '{"_redacted": true, "redaction_event_id": "...", "redacted_at": "..."}' AND redacted = 1 AND zeros change_note, source_filename in the same transaction. The PII bytes are physically gone from the DB.
  2. Render-time gates. Every consumer that reads a snapshot for display calls snap.safe_*() accessors that return None / "[redacted]" when snap.redacted is True. Defense in depth: even if a future bug missed the DB update, the render layer wouldn't leak.

What stays. The audit_event chain. The pii_redacted event records who requested it, the legal basis (PDPA §13 etc.), and the redaction_event_id. The hash chain proves the redaction happened at a specific time, on a specific snapshot, by a specific actor.

The bundle leak (W7-B1). Wave-7 audit's biggest blocker: change_note survived redaction in every consumer (timeline JSON, diff JSON, diff HTML, xlsx, bundle). Fix wired the safe accessors at every render boundary AND made the bundle exporter model_copy(update={"change_note": None, ...}) for redacted snaps. The lesson: every new PII-bearing column needs to be added to the safe-view contract from day one.

16. Magnitude-tiered drift classification

What A four-tier system (none / minor / material / major) that classifies how much a numeric field moved between two snapshots.
Where src/snapshot_timeline.py — _classify_pct + _compute_field_tier.

Why we need it. An analyst comparing 5 snapshots of Series A shares isn't asking "is the number different." They're asking "is the change material enough to require explanation in the memo." A 0.1% drift is noise. A 50% jump means something happened.

How it works. Two thresholds: 

MINOR_FRAC = 0.05      # ±5%
MATERIAL_FRAC = 0.20   # ±20%

def _classify_pct(prior, current) -> str:
    if prior is None and current is None: return "none"
    if prior is None or current is None: return "major"  # presence change
    if prior == 0 and current == 0: return "none"
    if prior == 0: return "major"
    delta = abs(current - prior) / abs(prior)
    if delta < 1e-9: return "none"
    if delta <= MINOR_FRAC: return "minor"
    if delta <= MATERIAL_FRAC: return "material"
    return "major"

Categorical fields (LP variant, AD variant, seniority rank) skip the percentage logic — any change is "major" (variant change is legally material; we don't try to quantify "more vs less generous").

Class-level overall tier is max(field_tiers) with ordering none < minor < material < major. The UI renders it as a colour-coded pill; diff_workpaper.xlsx fills the cell background with the matching colour so the analyst sees the same visual cues in the workpaper.

The NaN guard (W9-m6). Cap-table numeric fields should never be NaN. If a corrupt CapTable smuggles one in, _classify_pct raises ValueError — surfaces the corruption at the diff layer instead of silently classifying as 'major'.

What A Python library that renders an HTML + CSS document to PDF using its own layout engine.
Where src/pdf_memo.py — render_pdf_memo, render_diff_workpaper_pdf.

Why we need it. The audit memo and the diff workpaper PDF need to be hand-off-grade documents. Building them as Jinja-rendered HTML and then converting to PDF lets us reuse the Jinja template muscle (escaping, includes, loops) instead of hand-coding PDF primitives.

How it works. 

env = Environment(

What we rejected. ReportLab (low-level PDF primitive API — productive once you know it, but reusing Jinja templates was a bigger win). Headless Chromium (heavyweight, requires a browser dependency).

The pinned timestamp (M-1). PDFInputs.generated_at lets callers pin the cover timestamp to engagement.created_at so the memo is byte-stable per engagement state. Stronger than spec §8.10 carve-out (which permits wall-clock).

18. Audit loop discipline (stable finding IDs as test names)

What Every audit finding gets a stable ID. Every fix gets a regression test named for the ID. The finding's writeup explains the original context.
Where tests/test_wave{5..9}_audit_fixes.py; SYSTEM_AUDIT_*.md.

Why we need it. Audits surface bugs the builder didn't see. If you fix the bug without a test, the bug comes back the next time someone refactors that area. The audit doc becomes archaeology nobody reads.

How the discipline works.

  1. Audit assigns each finding a stable ID with severity prefix: B-W7-1 (blocker, wave 7, finding 1), W8-M3 (wave 8, major 3), SD-AUD-W9-B1 (stitched audit, wave 9, blocker 1).
  2. Audit doc explains what's wrong, includes a reproduction, suggests a fix sketch.
  3. Fix lands with one or more regression tests named test_w7b1_redaction_zeros_change_note_in_db etc.
  4. Comments in the fix code cite the ID: # SD-AUD-W7-B1: redacted snapshots drop the PII-bearing fields...

Now when a future change re-introduces the bug, the failing test name has the audit ID in it. The developer searches the codebase for the ID, lands on the audit doc, reads the original context, and fixes correctly instead of fighting the test.

The numbers. Across 9 waves: ~6 blockers, ~20 majors, ~50 minors found in audits. ~100 regression tests added that encode finding IDs in their names. The suite catches re-introductions reliably.

19. Header injection and open-redirect prevention

What Two adjacent attack classes against any route that takes a user-supplied URL and uses it in a redirect.
Where src/cookie_auth.py — _safe_next_url.

Open redirect. /login?next=https://attacker.example/clone. After login the server redirects to the attacker site. URL bar showed the legit domain, cookies got set legit, but the user lands on a clone where the attacker can phish them again. Common bug pattern in any auth flow with a next param.

Header injection. next=/legit%0d%0aLocation:%20attacker. The %0d%0a is CRLF. If the server stuffs the value unescaped into the Location header, the browser sees two Location headers and follows whichever its parser prefers. Used to be a serious bug class before werkzeug 3.x started raising on CRLF in headers — now it shows up as 500s instead of redirects.

The fix (both). 

def _safe_next_url(candidate, default=DEFAULT_NEXT_URL):
    if not candidate: return default
    # W8.1: any control char in candidate corrupts the Location header
    if any(ord(c) < 0x20 or ord(c) == 0x7f for c in candidate):
        return default
    p = urlparse(candidate)
    if p.scheme or p.netloc: return default       # absolute URL
    if not candidate.startswith("/"): return default
    if candidate.startswith("//"): return default # protocol-relative
    return candidate

Only same-origin path-only URLs survive. Everything else falls back to the safe default. Both attacks die.

20. Spec-driven development with amendment rounds

What A single source-of-truth spec document that the code references and the audit checks against. Amendments come in numbered rounds, not commit-by-commit edits.
Where SYSTEM_SPEC.md — 7 amendment rounds across waves 1-9.

Why we need it. Without a written spec, the code IS the spec. Audits become "find the bug" rather than "verify the code matches the contract." With a spec, the auditor can compare two things: "what the code does" vs "what the spec promises."

How the rounds work. Each round is appended as a new section (§11 round 4, §12 round 5, §13 round 6, etc.). Within a round, each amendment has a numbered subsection and references the audit finding it closes (e.g. "§13.1 CSRF on cookie-authenticated POSTs (closes wave-5 M-6)"). At the end of each round, re-tag the spec (e.g. spec-r6-2026-05-29).

The §9.6 error code inventory. One table that lists every error_code the API returns, the HTTP status, and where it comes from. Audits check the implementation emits only codes in the inventory; the inventory grows whenever a new code ships. This is how you avoid "the spec drifted from the code" silently.

The amendment-driven build pattern. Audit-finding → fix → spec-amendment → regression-test. Four artifacts that all reference each other through a stable ID. Future archaeologists land in any one and can follow the breadcrumbs to the other three.

pdfplumber Text extraction from PDF side letters. Pure Python. Image-only PDFs return a warning, not a hallucination.

One-paragraph summary

The cap-table reconciler is a Flask app with a Pydantic-validated parsing layer, a 60-rule deterministic checklist, a hash-chained engagement model on SQLite, byte-stable xlsx and PDF exporters, and a Big-4 portable bundle with offline verification. It uses HMAC-signed cookies plus a double-submit CSRF pattern for browser auth, a Bearer revocation deny list for API auth, optimistic concurrency with conditional UPDATEs for safe parallel mutations, calendar-hour rate limiting for cost containment, and content negotiation so one route serves both HTMX and JSON. The OPM Backsolve uses Black-Scholes-Merton tranche valuation with brentq for the root find — the analyst supplies every market input. Across 9 build waves with independent audits at each, 842 regression tests encode the lessons (every audit finding ID is a test name). Every prod-shaped knob has an explicit env-flag opt-in. The only remaining work is Evelyn-blocked: real SSO, Postgres swap, KMS, legal sign-off on the 90-day archival window, firm-specific rule content, and tenancy isolation.
