Cap Table Reconciler

The part of the cap-table workpaper that sits before the model. An expert-led tool for the international-valuations workflow: parse the messy file, point at every gap, persist the engagement, and hand the partner a Big 4 portable bundle. No fair-value opinion. No LLM in the calculation pipeline.

9 build waves · 9 independent audits 842 regression tests 60 deterministic rules across 6 pinned packs ~20k lines of Python and Jinja
Most analyst hours on a private-company valuation aren't spent on judgment. They're spent reconciling what the client sent. A stale option pool. A SAFE that should have converted at the last round. A side letter with terms nobody transcribed. An anti-dilution column that says "see charter." This tool ingests that file, points at every gap, and produces structured output an analyst can hand to an OPM, Backsolve, or DCF.

1. What it actually does

Walks one cap table from a raw .xlsx upload to a Big 4 portable bundle.zip. Every step in between is audit-defensible, byte-stable where the spec requires it, and hash-chained so an offline reviewer six months later can re-prove every decision.

Every arrow is a real HTTP endpoint with role-based auth, optimistic concurrency, a CSRF gate on cookie paths, and an audit-log event appended to a per-engagement hash chain.

2. The posture: expert-led, not algorithm-only

The tool is built around one founding constraint: the analyst keeps the judgment. The engine never picks volatility. Never picks a DLOM. Never decides whether a side-letter clause is material. Never computes a fair-value opinion. When the input is too messy to defensibly compute on, the tool refuses and writes the punch list. That refusal is the deliverable.

The engine DOES

  • Parse the messy .xlsx (date coercion, instrument-type aliases, embedded subtotals)
  • Run 60 deterministic rules with citations
  • Compute the breakpoint waterfall
  • Persist every snapshot immutably with a hash chain
  • Produce static + live-formula + DCF + memo + bundle exports
  • Run OPM Backsolve when the analyst hands it every market input
  • Track the chronological snapshot timeline with magnitude-tiered drift

The engine REFUSES to

  • Pick a volatility, TTL, or risk-free rate
  • Decide which AD variant the charter "really" means
  • Auto-convert SAFEs (too many opinions baked in)
  • Run an LLM over the side letter to extract terms
  • Compute a 409A opinion
  • Pass a sign-off if blocker findings stay unresolved
  • Render any field for a redacted snapshot, anywhere downstream

3. How a snapshot becomes a workpaper

Step 1. Parse

src/parser.py locates the cap-table tab by name pattern, finds the header row inside the first dozen rows even when title rows precede it, normalises eight common date formats to ISO, coerces instrument-type aliases (CCPS, RCPS, Ordinary) to the canonical enum, and skips embedded subtotal rows. Returns a CapTable Pydantic v2 model and a ParseReport listing every column it inferred and every row it dropped.

Step 2. Run the rule pack

60 hand-authored rules across six chronologically-pinned packs (v2026.1.0 through v2026.6.0). Each rule is a @rule-decorated function with a stable id, a severity tier (blocker / warning / info), and a citation. The engagement binds the head pack at creation time and freezes the bytes (bound_pack_json), so any later re-run uses the same pack the engagement was originally judged under.

Examples: G-AD-001 flags a preferred class with blank anti-dilution. G-WAR-002 flags a warrant past its expiry. G-SAFE-001 flags an unconverted SAFE past its trigger threshold. G-IN-002 flags a FEMA foreign-currency price-floor breach. Each emits a Finding with the rule id, severity, cited field paths, and the rule's citation.

Step 3. Adjudicate inline

The HTMX UI surfaces every finding with an inline form. Decision (free text or JSON) plus citation (required) lands as an immutable Resolution linked to the snapshot id. The hash chain appends a resolution_recorded event capturing who resolved what with what citation.

Step 4. Persist the engagement

Status lifecycle: open → review → signed → archived (with controlled 90-day restore window). Every transition gated on role permission and optimistic-concurrency version match. Every event appended to a per-engagement SHA-256 hash chain. The chain looks like: 

row_hash = SHA256(prev_row_hash || canonical_payload)
canonical_payload = event_type | actor | ts_iso | payload_json
genesis  = "00" * 32

Step 5. Export the workpaper

Five artifacts ship out the analyst's door:

4. The Big 4 hand-off

A Big 4 reviewer downloads bundle.zip, opens it on their laptop with no network, and verifies the engagement from genesis:

  1. Read audit_log.jsonl line by line.
  2. Start prev = "00" * 32.
  3. For each event, recompute SHA-256(prev_row_hash || canonical_payload) and confirm it equals the stored row_hash.
  4. Set prev = row_hash and continue.
  5. The final event's row_hash MUST equal manifest.audit_head_hash.
  6. For each file in the bundle, recompute SHA-256 and confirm it matches the manifest entry.
  7. Re-load rule_pack.json and re-run it against the head snapshot's cap table. Compare findings to the memo + the resolution events.

If any step fails, the engagement has been tampered with after generation. If every step passes, the reviewer has independently re-proven the entire analyst workflow without access to the running system.

Two surfaces, one engine

Every flow exists in both forms. The HTMX UI (/engagement/...?html=1) is the browser-driven analyst path. The JSON API is the same routes with Accept: application/json or no ?html=1. Content negotiation lives in one decorator (_engagement_errors) so error responses render the styled error page for the HTMX path and a stable error code body for the API path.

6. The audit loop that built it

Each wave shipped under the same six-step ritual:

  1. Build the planned items (5 to 13 per wave).
  2. Test with per-item regression coverage.
  3. Dispatch an independent auditor against ONLY the wave's deltas.
  4. Triage findings into fix-now vs defer with rationale.
  5. Fix with one regression test per audit finding code.
  6. Document in a BUILD_WAVE_N.md + SYSTEM_AUDIT_WAVE_N.md pair.

Every audit finding has a stable ID (B-W7-1, W8-M3, SD-AUD-W9-B1, etc). Every fix has a test named for the ID. When a future change reintroduces the bug, the test fails with the finding code in its name, and the audit doc explains the original context.

7. What each wave shipped

Wave 1 (foundation): parse + checklist + waterfall + live-formula xlsx

The walking skeleton. parse_excel turns a messy workbook into a CapTable. The checklist runs 8 rules. The waterfall computes breakpoints across non-participating, participating-uncapped, and participating-capped (including the senior-above-capped edge). The live-formula xlsx exporter writes a workbook the analyst can edit in Excel with the breakpoints and chart redrawing natively. 5 curated fixtures plus a holder-level stress test.

Wave 2: engagement model, hash chain, role-based auth, optimistic concurrency, PDPA redaction

Turned the demo into a system. SQLite-backed EngagementStore with a per-engagement append-only SHA-256 hash chain. Four roles (analyst, reviewer, partner, read-only auditor) with a permission matrix codifying SYSTEM_SPEC §3.2. Optimistic concurrency on every mutation via atomic conditional UPDATE plus rowcount check. PDPA right-to-erasure via a redaction sentinel that overwrites cap_table_json but preserves the audit log.

Wave 3: PDF audit memo, byte-stable bundle, rate limiting, subsequent events

The exporter half. WeasyPrint PDF memo with structured-fact pre-fill and explicit [ANALYST] placeholders. Portable bundle.zip with a SHA-256 manifest and an offline-verification recipe. Per-user calendar-hour rate limit (ExportRateLimiter) on memo + bundle. Subsequent-events rollup that anchors against engagement.head_snapshot_id so prior resolutions stay visible across snapshot uploads.

Wave 4: HTMX UI, DCF sidecar + template, valuation_date typing, what-if scenarios

The browser-driven surface. Content-negotiation per route so the same endpoint serves JSON to API clients and HTML to browsers. dcf_sidecar.py emits a named-range workbook the analyst points their DCF model at. dcf_template.py consumes the sidecar via Excel external-link references. valuation_date typed as date | None at the API boundary. /whatif HTMX panel for in-place sensitivity scenarios.

Wave 5: cookie auth, snapshot-aware what-if form, inline resolution, snapshot diff, rule pack v6 (60 rules)

HTMX usability + cookie auth + rule depth. HMAC-SHA256 signed session cookies (httponly, SameSite=Strict). Inline finding resolution form per row. Snapshot-aware /whatif form rendered per preferred class. Separate compute rate limit for /whatif. Rule pack grew to 60 across jurisdictional flags (FEMA, IRAS, §409A) and structural checks. First stitched system audit found 6 blockers at the wave seams; all closed in the same wave.

Wave 6: CSRF protection, Bearer revocation, startup collision check, cross-wave integration tests

The pre-prod hardening wave. Double-submit CSRF token pattern on every cookie-authed POST (Bearer paths exempt). Server-side Bearer revocation deny list (SQLite, WAL, 30-day TTL, hash-only storage). Startup guard refuses to boot on duplicate Finding.code across the rule registry. Cross-wave integration tests that drive one engagement through every wave's surface end-to-end, the audit's #1 ask after wave 5 caught 6 seam bugs that no unit test could find.

Wave 7: multi-snapshot timeline + N-way diff + xlsx workpaper export

The most analyst-visible wave. Chronological snapshot timeline UI. N-way diff endpoint accepting 2+ snapshot ids. Magnitude classification per (class, field) cell: none minor material major based on percentage drift, presence change, or categorical change. xlsx workpaper export with 3 tabs (Summary / Class Drift / Snapshots). Per-snapshot change_note field carries analyst rationale through to the workpaper.

Wave 8: prod-readiness sweep (every deferred audit item that didn't need Evelyn)

Demo-surface gates (ALLOW_STUB_SSO, ALLOW_PHASE_0_DEMO env flags). OCI engine-version env var (QAPITA_ENGINE_COMMIT). Three xlsx producers now fully byte-stable via shared xlsx_stability.py helper (pin workbook properties + rewrite zip envelope + scrub core.xml modified-timestamp). /readyz endpoint with SRE-grade state. Three ops CLI commands (prune-deny-list, prune-rate-limits, hard-delete-archived). Engagement archival with 90-day restore window. PDF memo auto-embeds snapshot drift section. Diff workpaper PDF (/diff.pdf) ships alongside the xlsx.

Wave 9: rule provenance in memo, OPM Backsolve route, vol-pack suggestions, CSRF rotation, snapshots pagination

Three Evelyn-independent capabilities plus deferred-item cleanup. PDF memo's findings table grew a "Rule provenance" column showing each finding's rule_id (pack_version) + citation. POST /engagement/<id>/opm runs OPM Backsolve against the head snapshot with the analyst supplying every market input (the tool refuses to pick volatility or DLOM). Vol-pack readback surfaces as analyst-overridable suggestions in the DCF sidecar Read-me sheet, not as defined names the DCF model auto-pulls. CSRF tokens carry an issuance-time prefix and rotate every hour. Snapshots pagination pushed into SQL. Rule-coverage CLI reports rule_id → fixtures.

9. How it helps an international-valuations analyst

Day 1 of a new engagement

Drag the client's .xlsx into the upload form. The parse report shows every column the engine inferred and every row it dropped. The findings page lists every gap, ranked by severity, each with a citation. The analyst goes through them in order. Within the first sitting, the engagement either has a clean head snapshot ready for downstream work, or a defensible refusal email to send back to the CFO.

Subsequent rounds

Every snapshot uploaded carries a change_note ("Series C closing 2026-03-15", "Q1 cap update from finance team"). The snapshot timeline page shows them all chronologically. The N-way diff endpoint compares any 2+ snapshots side-by-side with magnitude tiers per (class, field) cell. The same diff exports as a xlsx or PDF workpaper for the partner review meeting.

Sign-off

Partner clicks "Move to signed." The lifecycle gate refuses if any blocker finding is unresolved. PDF memo auto-generates with the "Snapshot drift" section auto-embedded so the partner sees what changed across the engagement's history without leaving the document. The "Rule provenance" column tells the partner exactly which rule caught what.

Big 4 review six months later

Reviewer downloads bundle.zip. Recomputes the hash chain offline. Re-runs the bound rule pack against the head snapshot without the running system. Diffs the recomputed findings against the memo. Every analyst decision shows up in the audit log as an immutable event with citation. The reviewer either agrees or has a surgical line to question, never a "the system did it" mystery.

11. What it's not

  • Not a 409A engine. No OPM allocation, no DLOM, no fair-value opinion.
  • Not an LLM tool. Zero language models in the calculation pipeline. Side letters stored verbatim; open-question lines surfaced for the analyst to adjudicate.
  • Not multi-tenant. Local-by-default with a documented production-cutover path.
  • Not a SAFE/note auto-converter. Too many opinions baked in (cap vs discount, pre vs post-money, MFN cascades). The analyst converts these to share classes during the mapping step.
